## Problem Statement

The current scoring engine (`src/scoring/scorer.js`) evaluates **repo metadata** (stars, forks, creator fame, commit count) but never reads the actual skill content. This is like rating a restaurant by the chef's Twitter followers without tasting the food.

Results: 7/8 repos score S-tier, technicalQuality variance = 0.38, relevanceScope variance = 0.19. Two dimensions carrying 35% of weight contribute near-zero discrimination.

The user needs a scoring system that can efficiently triage 100+ skill repos to decide "should I spend time trying this?" — prioritizing content quality over vanity metrics.

## What Makes This Cool

A framework that can **read the actual SKILL.md files** and assess prompt engineering quality — behavioral precision, failure handling, anti-rationalization engineering — not just count stars. Paste a GitHub URL → get a content-quality report in seconds.

The "wow" moment: a static analyzer + LLM-as-judge pipeline that understands what makes a Claude Code skill *good* at the prompt level.

## Key Insight: What IS a Skill?

From AEE double-blind analysis (2 independent Opus agents reading all skill repos):

> "A Claude Code skill is a **structured prompt that transforms Claude from a general-purpose assistant into a specialist with a defined methodology, workflow, and set of constraints**. It is NOT code. It is an operating manual injected into context."

### Four Skill Archetypes
1. **Workflow Skills** (gstack `/ship`, `/review`) — Multi-step pipelines with gates, conditions, escalation
2. **Methodology Skills** (superpowers TDD, debugging) — Encode a philosophy with hard constraints
3. **Knowledge/Convention Skills** (antfu-skills) — Reference material for a technology/codebase
4. **Orchestration Skills** (superpowers brainstorming) — Meta-skills coordinating other skills

### Three Highest-Quality Prompt Engineering Patterns
1. **Iron Laws + Rationalization Prevention** (superpowers) — Explicitly naming how the AI will shortcut, then blocking each rationalization
2. **Structured Preamble + State Management** (gstack) — Every invocation starts from known state
3. **Two-Stage Review Loops** (superpowers subagent-driven-dev) — Separate spec compliance from code quality review

## Constraints

- Must handle 100+ skill repos efficiently
- Static analysis should be free and instant (~seconds)
- LLM evaluation should be cheap (~$0.10-0.15 per skill, ~$15 total for 100 skills)
- gstack = reference standard (~80/100 points)
- Weights are initial estimates — need validation via test runs and calibration
- Creator credibility stays important but at reduced weight (25% → 5-10%)

## Premises

1. **Screening > Ranking** — The goal is "should I try this?" not "is #3 better than #4?" ✓ Agreed
2. **Content > Metadata** — What the SKILL.md actually says matters more than GitHub stars ✓ Agreed (AEE consensus)
3. **Creator credibility stays at 25% weight** — User prefers keeping creator signal strong ✓ Agreed (user override)
4. **Weights need validation** — Initial weights are hypotheses, need test-and-adjust ✓ Agreed

## Approaches Considered

### Approach A: Content-First Full Rebuild (CHOSEN)
**Effort:** human ~2 weeks / CC ~1 hour
**Completeness:** 9/10

Completely redesign dimensions from skill-content perspective:

**Tier 1: Content Quality (50%)**
- Workflow Structure (12%) — Phase/step count, decision branching, completion protocols
- Behavioral Enforcement (12%) — Iron Laws, Red Flags, rationalization prevention, guardrails
- Error Resilience (8%) — Escalation paths, BLOCKED/NEEDS_CONTEXT, retry limits
- Theory of Mind (8%) — Anticipates agent shortcuts, user confusion, edge cases
- Instruction Clarity (5%) — Unambiguous, actionable, correctly sequenced
- Domain Depth (5%) — Technical accuracy, reference quality, practical examples

**Tier 2: Engineering Quality (20%)**
- Testing (8%) — Test file count, test types (unit/integration/e2e/LLM-judge)
- Infrastructure (5%) — Build system, template generation, CI/CD
- Cross-skill Composition (4%) — References to other skills, declared dependencies
- Cross-platform Support (3%) — Supports Claude Code + other agents

**Tier 3: Ecosystem Signals (30%)**
- Creator Credibility (15%) — Tier classification (S/S-/A/B/C → 10/8.5/7/5/2)
- Community Validation (8%) — Stars, marketplace listing, awesome-list inclusion
- Maintenance Activity (5%) — Commit velocity, contributor count, issue response time
- Usage Evidence (2%) — Telemetry, testimonials, downstream adoption

> NOTE: Weights above are adjusted from pure AEE recommendations to respect user's preference for 25%+ creator weight. Creator 15% + Community 8% + Maintenance 5% ≈ 28% total "who made it & who uses it" signal. Content-only dimensions = 50%. To be validated via test runs.

### Approach B: Incremental Fix (NOT CHOSEN)
Quick deduplication + S/S- split. 4S/4A instead of 7S/1A. But still metadata-only evaluation.

### Approach C: Hybrid B→A (NOT CHOSEN)
Two-phase: fix now, rebuild later. Risk of throwaway code.

## Recommended Approach

**Approach A: Content-First Full Rebuild.**

Reason: AI makes completeness nearly free. The fundamental insight from AEE is correct — evaluating skill quality without reading the skill is broken by design. No amount of metadata tuning fixes this.

## Measurement Strategy

### Phase 1: Static Analysis (free, instant)
For each SKILL.md file, extract:
```
step_count          — Number of ## Step / ## Phase headings
command_count       — Number of bash/shell code blocks
conditional_count   — Number of if/else/when decision points
error_token_count   — STOP, BLOCKED, escalate, "never", "do NOT"
anti_pattern_count  — BAD:, rationalization tables, common failures
table_count         — Structured rubrics and decision matrices
cross_skill_refs    — References to sibling skills
has_frontmatter     — Valid YAML with name/description/allowed-tools
has_completion_protocol — DONE/BLOCKED/NEEDS_CONTEXT
has_escalation      — Explicit escalation format
total_word_count    — Overall depth
reference_file_count — Progressive disclosure via references/
```

### Phase 2: LLM-as-Judge (~$0.10 per skill)
Feed SKILL.md content (truncated to ~4K tokens) to Haiku with gstack `/review` as reference standard:
```
Rate 1-10 on:
1. INSTRUCTION CLARITY
2. THEORY OF MIND (anticipates shortcuts/confusion)
3. WORKFLOW COMPLETENESS (start → happy path → error → escalation → completion)
4. BEHAVIORAL ENFORCEMENT (Iron Laws, Red Flags, rationalization prevention)
5. DOMAIN ACCURACY
```

### Phase 3: Runtime Signals (future)
- Invocation frequency (skill telemetry)
- Completion rate (DONE vs BLOCKED)
- Re-invocation rate (retry within 10 min)
- Session duration

| Practice | Source | How We Apply |

| Issue response time | npms.io | Maintainer responsiveness (future, via GitHub API) |

## Open Questions

1. **Weight calibration** — The 50/20/30 split (Content/Engineering/Ecosystem) needs test runs. User noted weights may need adjustment based on validation.
2. **LLM-judge model choice** — Haiku for cost? Sonnet for accuracy? Need benchmark.
3. **Knowledge vs Workflow scoring** — Should knowledge-base skills (antfu) be scored on a different rubric than workflow skills (gstack)?
4. **Scoring scale** — 0-10 or 0-100? AEE used both. 0-100 gives more granularity.
5. **Creator weight** — AEE recommends 5-10%, user wants ~25%. Current design uses 15% as compromise + 8% community + 5% maintenance ≈ 28% total ecosystem weight.

## Success Criteria

- Score spread: at least 40-point range (vs current 1.6-point range on 10-scale)
- Tier distribution: clear S/A/B/C separation with no more than 40% in any single tier
- antfu-skills scores meaningfully lower than gstack (content difference reflected)
- New skill added → full score in <30 seconds (static) or <2 minutes (static + LLM)
- 100 skills evaluated for <$15 total LLM cost
